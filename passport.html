Attacks the interface alone can’t stop

Every attack has a defence.

AttackSomeone edits the result, image or operator
The signature covers the result, image hash, job, part, station and session, so any edit breaks it.
AttackA genuine event is replayed for extra credit
The server remembers every event ID and device sequence. A retry returns the first receipt and never counts twice.
AttackAn admin quietly changes a past decision
Originals never change. Corrections are added as new signed records, and audit checkpoints are protected separately.
AttackValid signature, but the wrong part or person
A signature can’t see what was under the camera. Bind the fixture, part ID, cycle trigger and work session as well.
AttackAn older camera can’t sign anything
Sign at a hardened edge gateway instead, and label it “gateway-verified”, never “camera-verified”.
AttackThe connection drops or the clock changes
Queue signed records on the edge, show “pending verification”, and flag gaps in the sequence.
Transport + identity

Two identities. Two doors.

  • Factory devices use certificates and mutual TLS
  • WeChat users get short-lived sessions for one factory
  • A user session can never submit device evidence
  • No secrets or private keys inside the Mini Program
Confidentiality

Keep the raw image private.

  • Everything encrypted at rest
  • Every view and file is permission-checked
  • Shared passports hide drawings, part IDs and raw scores
  • Screenshots can’t be fully prevented on every device
Before production

Prove the trust boundary.

  • Test cameras, key storage and firmware controls
  • Test identity binding and offline behaviour
  • Agree retention, deletion and the China data model
  • This prototype is not a security certification

Signed
What the factory device signs

Never sign just “PASS”.

Every inspection is sealed with its full context, so nobody can quietly change it later:

schema versiontenant / sitedevice IDboot epochsequenceevent + capture IDscapture timework sessionpart instancework orderrevisionoperationparticipant rolesfeature IDvalues · units · limitscamera resultmodel / recipe versioncalibration refhashes of originals

The server adds its own signed receipt. It never rewrites the signed bytes.

Tip: the FDM feature ID is a permanent identifier, not a balloon number, so renumbering a drawing never breaks the evidence chain.
Before the pilot

Try to break it first.

Each of these should fail loudly and visibly, not silently.

Identity + access5 tests
  • Forwarded or expired QR
  • Role escalation
  • Ex-employee still logged in
  • Another factory’s evidence ID
  • Stolen account recovery
Evidence + integrity6 tests
  • Edited result or image
  • Replayed signed event
  • Revoked device key
  • Deleted record
  • Swapped part
  • Changed model recipe
Quality + assessment5 tests
  • Valid signature on a failed part
  • Final QC reversed
  • Operator reassigned
  • Expired qualification
  • Supervisor tries to edit raw evidence
Operations + onboarding6 tests
  • Lost connection
  • Half-finished upload
  • Sequence gap
  • Counter reset
  • Time to first task
  • Time to first accepted evidence
A pass rate is not a skill score.

Part outcomes also depend on the machine, material, tooling, gauge and task difficulty. Start with traceable task experience and assessor-reviewed observations; formal qualification needs an approved assessment process.

Implementation fit: reuse ConnectIQ’s shared REST / .NET services and SQL data model where it fits. Check SQL Server / Azure SQL Ledger support for your actual deployment before relying on it. One logical product does not require copying every customer’s raw data across borders.
