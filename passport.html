Live local cryptographic demonstration

Change the result. Break the signature.

This lab really signs sample bytes with Web Crypto (ECDSA P-256 / SHA-256). It is not the simulated verification used in the phone. Keys and replay tracking exist only in this page; there is no production trust anchor.

Ready. No keys or inspection data leave this page.
Image hash: not generated

The image bytes are a synthetic text fixture, not a camera frame. The demo signs exact serialized bytes (formatting changes also invalidate the signature); production should use a tested signing format such as JWS and an agreed canonicalization policy. After one successful ingestion, verify the same event again to see duplicate rejection. Re-signing resets this local lab.

Controls that the UI cannot provide

What each control actually protects.

Changed result, image or operator field

Verify the digital signature and image digest, including job, part, station and session in the signed payload. A hash stored beside an editable image is insufficient.

Authentic event, replayed for another reward

Persist unique event IDs, device sequence / boot epoch and consumed challenges on the server. Idempotent retries return the first receipt; never count twice.

Administrator edits a past decision

Keep immutable originals and append a signed amendment. Independently protect audit checkpoints; an ordinary SQL row lock is not an integrity guarantee.

Valid signature, wrong physical work

A signature cannot prove the correct part was placed in the camera or the named employee did the work. Bind fixture / part identification, cycle trigger, work session and observed roles.

Legacy camera has no signing capability

Sign on a hardened edge gateway at first trusted receipt. Display “gateway-verified,” not “camera-origin verified.” The camera-to-gateway path remains a trust boundary.

Connection drops or camera time changes

Queue signed records on the edge. Show “pending server verification,” preserve capture and receipt times separately, and investigate sequence gaps or counter resets.

Transport + identity

Two identities. Two API surfaces.

Use enrolled device certificates and mutual TLS for the edge. Use short-lived, tenant-scoped user sessions for WeChat. A user session cannot call the device evidence ingestion API. Never embed AppSecret, device private keys or shared signing secrets in a Mini Program.

Confidentiality

Keep the raw image private.

Encrypt objects at rest. Authorize every view and evidence object. Use an authenticated media proxy or carefully scoped short-lived URLs. Shared passport views exclude customer drawings, part IDs and employee raw performance data by default. Screenshots cannot be reliably prevented.

Before production

Validate the trust boundary.

Test camera interface, key storage, firmware controls, identity binding, offline behavior, model validation and deletion / retention policy. Decide the China deployment and data-transfer model explicitly. No feature in this wireframe constitutes a security certification.

Proposed module boundary

One backend. Several ways to do the work.

First-time worker

Invite → bind → work

Use an opaque, expiring invitation with server-side scope. Pre-fill the factory and assigned employee role after appropriate authentication. Verify employer membership separately from the WeChat account. No email, password, résumé, phone number or certificate upload is required by this proposed first-use flow.

Returning worker

Scan → confirm task

Reuse the existing account-to-employee binding after checking current employment and role validity. Route back to the intended job after authentication. Refresh station / operation sessions at handover; never borrow yesterday’s operator attribution.

Public QR visitor

Try → request access

Show synthetic examples without production tenant access. A shared factory QR is an entry point, not an authorization credential. An invitation alone must not grant employer-verified status.

POST /auth/wechat/exchange Mini Program exchanges a temporary login code through the backend. Server-side AppSecret. Map (AppID, OpenID) to an internal user; issue a scoped application session.

Minimum evidence contract

Do not sign just “PASS”.

Sign the schema version, tenant / site, device identity, boot epoch, sequence, event and capture IDs, capture time, work session, part instance, work order, revision, operation, participant roles, feature ID, values / units / limits, camera result, model / recipe versions, calibration reference, and hashes of all original artifacts. The server adds a separate signed receipt and verification decision; it does not rewrite signed bytes.

FDM feature ID is a persistent characteristic identifier—not just a balloon number. Map it to drawing revision and operation so a renumbered balloon does not break the evidence chain.

Use stable decimal-string conventions or explicit scaled integers for dimensional data. Treat deduplication keys, identity claims and retention policies as server-side rules, not fields that a mobile client can authorize.

Acceptance tests before pilot

Make failure visible.

Identity + access

Forwarded / expired QR, role escalation, stale employment, cross-tenant evidence ID, stolen account recovery.

Evidence + integrity

Alter result or image; replay signed event; revoke device key; delete a record; substitute a part; change the model recipe.

Quality + assessment

Valid signature on a failed part; final-QC reversal; reassigned operator; expired qualification; supervisor cannot alter raw evidence.

Operations + onboarding

Connectivity failure, incomplete object upload, sequence gap, counter reset; measure time-to-first-task and first accepted evidence separately.

Do not infer a human skill score directly from pass rate or Cpk. Part outcomes also depend on machine, material, tooling, measurement system and task difficulty. Start with traceable task experience and assessor-reviewed observations. Formal qualification requires an approved assessment process.

Suggested implementation fit: reuse ConnectIQ’s shared REST / .NET services and SQL data model where appropriate. Assess SQL Server / Azure SQL Ledger availability for your actual deployment; do not assume the existing version supports it. A single logical product does not require cross-border replication of every customer’s raw data.
